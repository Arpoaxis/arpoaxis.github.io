Problem and project scope

Restaurant reservations involve more than recording a time and a party size. Customers need a usable booking flow, while hosts and managers need consistent information about seating, waitlists, staff activity, and tables across a restaurant. In a five-person software engineering team, we built a Java web application that connects these workflows to a relational database.

This is an academic team project from 2025, developed using Java 17, Jakarta Servlets/JSP, Maven, Apache Tomcat, SQLite, and JDBC. The features below describe the shared application's implementation, not work claimed entirely by one team member.

How the application works

01

Customer reservations

A signed-in customer selects a restaurant, date, time, party size, and optionally a table. The servlet validates date/time inputs before sending the booking request to the database layer.

02

Seating and table availability

For a selected table, the DAO checks overlapping one-hour booking windows, ignores cancelled bookings, and creates the booking and table assignment in a single transaction.

03

Staff and waitlist operations

Staff-facing views display restaurant bookings and waiting guests. Hosts can enter walk-ins, and staff workflows support booking statuses and seating operations.

04

Manager reporting

Dashboard queries summarize total bookings, daily bookings, distinct customers, and counts by status. The DAO queries can be scoped to an associated restaurant.

Architecture

The project follows a server-rendered web application structure: JSP pages present the interface; Java servlet handlers receive requests, validate input, and route operations; DAO classes work with SQLite via JDBC. Supporting filters and sessions provide role-aware access to administrative screens.

Database design

The initializer defines separate tables for restaurants, users, bookings, restaurant tables, waitlists, and roles. Junction tables represent booking-to-table assignments and user-to-role memberships, rather than storing multiple IDs in a single field.

Interesting engineering decisions

Preventing overlapping table bookings

Before assigning a specific table, BookingDao.createBookingWithTable queries for bookings whose one-hour occupancy window overlaps the requested period. The method uses setAutoCommit(false), commits the booking and link together, and rolls back on failure. This keeps the two inserts coordinated. It is a coursework implementation, not a claim of independently verified concurrency safety at production scale.

Validating dates and time slots

BookingCreateServlet checks that a booking date is not in the past and, for this project, restricts time selection to 11:30 AM–10:00 PM in 15-minute increments. Failed validation returns users to the form with an explanatory message.

Role-aware staff interfaces

The application distinguishes ADMIN, MANAGER, HOST, and EMPLOYEE roles. An authorization filter controls access to administrative routes, while individual staff servlets also check session and role information. This demonstrates application-level authorization logic, but the project has not been presented as a security-audited production service.
